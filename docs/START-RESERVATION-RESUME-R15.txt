2. ARTIFACTS, SCHEMA, PRODUCER AND CONSUMERS
The host reservation is a transient port/exclusivity reservation returned by
host.reserve(). The maintenance gate is a distinct .execution.maintenance
file created exclusively and released in finally. Neither is the Start audit.
START_RESERVED and the Start record ARE THE SAME artifact:
var/recovery-<RunId>.json.start. There is no separate reserved-phase file.
RecoveryWorkflow.reserveStart produces it with exclusive creation and fsync;
v2 Start creation/reuse also runs the native migrationAuditBarrier on it.
Its payload is version:1, state:START_RESERVED, pid, at, approved head,
bootstrap:boolean, before:full captured evidence with gate:null, and lineage.
V2 producers include ledgerProtocolVersion:2; migration adds
migrationTransactionId equal to the validated completion transactionId.
Older native-v2 reservations without ledgerProtocolVersion remain supported;
the captured v2 envelope determines the launch protocol, without rewriting.
Lineage is version:1, auditHash, runId, head, root, phase:start,
predecessorHash:the byte hash of this run's Disarm completion.
before contains artifact value+SHA-256 (or null) for AutoLive, authority and
locks, Schedule, PROGRAM, ledger, WAL, marker, Scheduled journal and lock,
maintenance record, media manifest/delete journal and migration artifacts.
The v2 envelope and WAL bind repositoryId, ledgerId, snapshot and history.
The immutable approved HEAD selects the trusted helper/gate hashes. Current
storage capability is checked at initial review, reserved recheck and reuse;
migration additionally binds it to intent.native (including volume identity).
Native v2 without migration has no historical volume field in the existing
schema: it uses the canonical path, exact envelope/WAL bytes, approved helper
identity and current local NTFS capability; no historical volume is invented.
Consumers: ControlledStart (launch options, evidence and READY predecessor),
RecoveryLineage (phase validation), prepareReview (phase review), and
restoreReview/verifyRestoreAuthority (history validation and configuration
Restore). READY is a distinct .ready artifact; it does not replace .start.

3. ORDER AND RESUMABLE PREDICATE
Prepared -> explicit offline Disarm plan -> Disarm completion -> Start review
-> transient host reservation -> fresh Start review -> maintenance gate
-> migration recovery when needed -> durable .start -> gate/host release
-> fresh canonical census and evidence -> launch -> ownership/readiness
-> native authoritative ledger anchor -> durable .ready.
Reuse requires exact R12 lineage through Disarm completion and Start; matching
schema/head/bootstrap/migration transaction/protocol; valid informational pid
and timestamp; exact saved.before versus current normalized evidence; a
usable closed ledger (or explicitly approved absent-ledger bootstrap); no
authority/Scheduled/ledger owner requiring reconciliation; no pending ledger
transaction; no Restore phase or READY; and current host/root/HEAD/service,
Schedule, audited disarm, maintenance and native checks passing.
The saved pid is NOT process ownership evidence and is never used to infer
that its process died or to authorize a second owner.

4. CURRENT REVALIDATION
startReview reruns preflight: approved repository identity, canonical offline
census, Stopped/Disabled service, free 8080 except the held reservation,
MediaMTX identity, bootstrap permissions, canonical realpaths, Schedule and
maintenance gate. It validates the audit, Disarm hashes, authoritative hashes,
ledger/WAL consistency, migration state and native helper/capability.
offline compares full initial and reserved reviews BEFORE acquiring the gate.
Existing reservations are validated at that initial boundary, before any
migration; an additional owned-gate review precedes reuse. ControlledStart
compares evidence after release and again immediately before launch, after
the before-controlled-launch hook. A changed phase or current state rejects.

5. FOREIGN/STALE POLICY
Wrong RunId/HEAD/root/audit/predecessor, copied records, wrong bootstrap or
migration linkage, malformed/truncated records and stale current evidence
reject; no unlink, replacement, migration or launch follows. Existing foreign
artifacts are retained. Rejection tests compare the entire TEMP file tree,
including bytes and mtime. A race discovered after taking a transient gate
still releases only the gate/reservation owned by this operation.

7. LAUNCH BEFORE READY
Canonical process/port evidence blocks retry while an owner may exist.
Authority/Scheduled/ledger locks and unresolved WAL state require canonical
reconciliation; a PID alone is insufficient. If runtime progressed and then
cleanly drained without READY, its authority epoch/WAL differ from .start;
this lineage still rejects and requires a new recovery path. There is no
implicit adoption, lock deletion or automatic second launch.

8. READY EXISTS
controlledStart checks for .ready before reserveStart. It reruns the existing
offline Restore authority/lineage verification twice and compares fresh
state, service and media. It requires exact READY authority epoch and current
AutoLive/Schedule/PROGRAM hashes, valid R12 READY and authoritative ledger
successor evidence, and no Restore phase. A completed offline retry returns
{owner:null,result:ready} read-only; it does not create a gate, epoch or owner.
An online owner, conflicting/stale READY, stale gate or unresolved ledger
rejects and preserves canonical reconciliation requirements. Direct
reserveStart rejects READY_ALREADY_EXISTS rather than authorizing a launch.

9. MIGRATION PRESERVATION
Clean migration and interrupted intent/installation are still reviewed before
mutation under the R13 host reservation and maintenance gate. First Start
finishes migration before creating .start. Completed migration before .start
can still create it. Completed migration after .start now validates and reuses
it without invoking startHeld or duplicating migration. A saved reservation
with an unresolved v1 migration is rejected before migration mutation.
