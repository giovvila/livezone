# Partial migration staging recovery — R26

Recovery `Prepare → prepareReview → preflight → capture → artifact → readEvidence → capturedEvidence` previously applied strict text decoding to `migrationIntentStage` before `CleanLedgerV1Migration.view()` could classify its exact bytes. A torn final multibyte character therefore failed with `PERSISTENT_EVIDENCE_INVALID_UTF8`, despite being an expected intent prefix.

Completed authoritative records (`intent`, `activated`, `completed`, canonical ledger, bootstrap, authority and WAL text) retain strict UTF-8 and their existing JSON/schema/checksum/provenance checks. Migration-owned temporary streams are exactly `intent.stage`, `base.stage`, `snapshot.stage`, `activation.stage`, and `completion.stage`. No filename-wide `.tmp` exemption exists.

The migration owner now supplies opaque evidence for the one staging stream included in general recovery capture: `intent.stage`. Its ordinary-file bounded raw Buffer is hashed before interpretation; the audit stores SHA-256 and byte length with a staging marker, never parsed partial JSON or replacement-decoded text. The owner's `view()` still reads all five staging streams as raw Buffers and checks their byte-exact expected representation and protocol ordering. General `artifact()` and `PersistentEvidence` remain strict even if explicitly called on a stage path.

Classification order is: host/offline proof, immutable evidence capture (completed text strict, owned intent staging opaque), recovery authorization/audit checks, migration `view()` classification and native identity proof, final Prepare authorization, protocol resume. An opaque capture is not validation or permission to mutate. Random bytes, another identity, wrong prefix, malformed JSON, wrong schema, oversized streams and unexpected/order-invalid artifacts fail closed before migration writes.

The staging predicate is `Buffer.from(expected).subarray(0, partial.length).equals(partial)`, including empty streams and the complete expected representation. A stream longer than expected fails equality. Expected bytes include newline, sealed/checksummed intent, deterministic transaction identity and exact original ledger, bootstrap, authority, repository path/root and verified native capability. The prefix can end anywhere, including inside a multibyte character. It is never decoded. Later stages are derived from that same validated intent; existing order checks remain mandatory.

Canonical Prepare retry appends only the missing suffix of the identical expected intent, syncs the file, performs the existing namespace barrier, rechecks guards and authorization, verifies full byte equality and durably replaces the stage with intent. It does not delete ambiguous evidence, generate a new migration, change v1 history, create WAL or execute runtime. Prepared is authorized separately afterward. R24 maintenance/evidence callbacks remain unchanged.

Start shares recovery capture and `view()/durable()/prepareHeld()`. Ordinary workflow Start follows Prepared, so a legitimate crash at that point normally leaves a durable intent and possibly later binary stages. The lower-level migration Start/resume contract also supports INTENT_STAGING through the same Prepare implementation; a regression completes that path and verifies preserved consumed history. No separate decoder or recovery rule is introduced.

Changed production files: `server/recovery/CleanLedgerV1Migration.js` (owner evidence capture) and `server/recovery/RecoveryContract.js` (dispatch only the known owned intent stage). Support: optional Unicode suffix in `RecoveryIntegrityFixture.mjs`. Tests: new partial-staging regression suite; R20 separates opaque staging capture from the unchanged strict completed-record matrix. `PersistentEvidence.js`, migration predicates/writer/durability, `RecoveryWorkflow.js` and native helper are unchanged by R26.

Review logs, test manifests, RED reproduction and preservation evidence are under `tmp/r26-review`; these are review-only. Final verification totals and preservation outcome are recorded in `tmp/r26-review/FINAL-REPORT.txt`.
